# P12.8 owner wire and signature foundation: adversarial review

Status: **SOURCE FOUNDATION ONLY; OWNER HTTP DISABLED; P12.8–P12.12 OPEN**
(2026-09-27). The approved [P12.7 decision](phase12-7-decision.md) remains
the consumer contract. The [execution prompt](phase12-7-12-execution-prompt.md)
orders the remaining implementation and target gates.

## Scope and evidence

- A fixed Owner-HTTP/1 operation registry binds numeric values to exact
  `POST` paths. The portable digest builder hashes the canonical binary
  signing input, including exact decoded ciphertext and 16-byte tag. A vector
  computed independently with Python `hashlib`/`struct` agrees with C++.
- A single pending 30-second challenge binds full device, boot, owner-key
  digest, encrypted session, owner epoch, profile generation, operation,
  request ID and challenge. Its first complete attempt consumes it before
  signature verification; timeout and monotonic rollback cancel it. `take`
  returns the digest of the **same signing fields** only after that binding
  matches. The caller must still validate the current journals/session and
  inactive output before invoking it.
- The Pico PSA adapter checks a canonical on-curve P-256 SEC1 public point,
  raw `r || s` ranges and low-S normalization, then verifies the 32-byte
  Owner-HTTP digest. A fixed P-256 signature independently generated by the
  pinned Noble implementation passes; altered digest, signature and point,
  high-S and zero signatures fail.
- Host build and complete CTest pass **99/99** with the pinned Mbed TLS
  checkout. The affected three owner tests passed again after the repairs
  below. The RF-inhibited Pico 2 W cross-build passes, with one SRAM BOOTSEL
  callback and no linked core-1 launcher. Its unflashed UF2 SHA-256 is
  `784819323c64fce6796f9b7f79ef004df1080eed230ff2ef55bfd4769f826c57`.
  `nm` confirms the new owner and claim symbols are **not linked** into the
  image: the firmware has no owner route to reference them. This is compile
  evidence only, not target behavior or resource acceptance.

## Findings, repairs and second assessment

| Adversarial finding | Repair and affected check |
| --- | --- |
| A future handler could consume a challenge using one caller-built record, then verify a signature over different fields. | `take` now accepts the actual `OwnerSigningFields`, session and owner-key digest, derives the candidate binding itself and returns the digest of those same fields. `owner_challenge_tests` rerun. |
| A generic 2,048-byte sealed-body cap could admit an ordinary operation beyond its bound. | Enforce 1,024 decoded bytes for ordinary operations and 2,048 only for client enrollment; tests cover both edges. The HTTP handler must additionally enforce the raw JSON-body limit. |
| Issuing after monotonic rollback could cancel a pending challenge and immediately accept a new one on the same rolled-back clock sample. | Cancel and reject that issue; focused rollback test rerun. |
| A zero generation could enter the signed owner path even though consumer ownership starts only after a committed profile. | Both digest and challenge issue require a nonzero profile generation; focused negative tests rerun. |

The second assessment traced each operation/path, device, boot, epoch,
generation, session, owner-key digest, challenge, request and expiry binding.
It found no further actionable defect within these **disconnected** components.
The signature verifier and challenge slot are core-0 serialized primitives;
they cannot authenticate a browser by themselves. The HTTP route, session
start/finish transcript, claim envelope, entropy, generated CA/server
identity, transactional activation, Safari client and station mTLS enrollment
are still missing. The raw HTTP parser must cap body size independently of
the decoded sealed-body cap.

The historical brief core-1 sampler failed under a physical press. A later
[whole-gesture target run](phase12-8-bootsel-window-target.md) observed a
human press/release with core 1 active and AP recovery; it did not implement
an owner claim. The exact `fb091f8` image and no-hardware statement above
describe this earlier owner-wire source slice, not Candidate A's current
installed image.

## Session-finish transcript continuation

The initial wire document said the finish signature covered the start body
without defining exact bytes. The continuation defines a canonical decoded
start-request digest, a fixed-order session transcript `S`, a
domain-separated finish digest and `SHA256(S)` HKDF salt. All bound fields,
including the owner-key digest and session expiry, have exact positions and
encodings. Independent Python `hashlib`/`struct` vectors for all three
digests agree with the portable C++ builders; altered-binding cases reject
the original digest.

Adversarial review found that the first start-digest helper incorrectly
required boot/response fields that do not exist at session start. It now
validates only the four decoded start fields; finish and salt require the
complete session. A focused test caught the old all-fields expectation and
was corrected to assert that a start-only request can be hashed while finish
cannot. The focused owner wire/challenge/signature tests pass 3/3, and the
RF-inhibited Pico 2 W default image cross-links with its topology checks.
The second assessment found no further defect in these disconnected
transcript builders. Session routes, X25519/HKDF/AEAD execution, owner-key
selection, expiry and journal admission remain open; no live owner authority
is enabled.
