## Selected architecture and topologies

Use **controller/member** for radio control and **collector/sender** for logging. Any Pi can be a logging collector regardless of Fleet role. One destination per sender, IPv4 unicast only, export and listening disabled by default. A collector can receive from up to 32 explicitly configured IPv4 peers; a member can export its native application events and up to eight selected USB Picos. External RFC 5424 collectors can store the same records; interpretation of the compact project MSG is an external integration concern.

| Path | Initial behavior |
| --- | --- |
| Pico → collector Pi | Station IPv4 sender, no USB or Fleet enrollment required. |
| Pico → external collector | Same RFC message, configurable destination port including 514. |
| Member Pi → collector Pi or external collector | Selected native application logs only; no general host-journal export. |
| Pico → USB member Pi → collector Pi | Member preserves origin and adds exactly one relay observation. |
| Many members/Picos → collector Pi | Per-peer admission, bounded queues and scoped source filters. |
| Direct Pico UDP plus USB-forwarded copy | Both may appear with separate ingress provenance; no cross-trust suppression. |
| Collector → another collector | UDP ingress is never eligible for export; no collector-chain forwarding. A collector may independently export its own native/USB records. |

Select a small application-owned C++ service, proposed name `wsprrypi-log.service`, with a journal reader, bounded forwarding worker and optional UDP listener. It uses existing libsystemd support, POSIX IPv4 datagrams and no new general logging daemon. Rsyslog/syslog-ng are capable alternatives but would add configuration ownership, distro/package variation and identity/routing transformations for USB-origin events. Leave installed logging stacks untouched. A dedicated service also avoids parsing hostile datagrams inside the current root transmitter process. Reuse portable record validation rather than duplicating USB parsers or adding Pi dependencies to firmware.

The service reads eligible records from the real `wsprrypi.service` journal starting at the current tail, follows native and verified USB entries, and writes imported UDP records to its own journal unit. It must verify trusted journal unit, local collector ID and ingress before forwarding. Its own diagnostics, systemd manager messages, old records missing sequence/session identity, and every UDP import are ineligible. Journald disabled/unavailable means forwarding unavailable; report that condition rather than silently changing native logging settings. Service restart starts at the tail: no durable replay/spool or cursor catch-up. Journal rotation invalidates the reader cursor, increments a discontinuity counter and resumes at the current tail.

## Origin, relay and trust

Retain the common logical `wsprry-log/1` fields and meanings without changing that closed USB contract. Stable Pico ID is its WTP device ID. Pi ID remains the existing domain-separated machine-ID hash; raw machine ID is never exported. Origin boot is the existing logger process/boot identity, not journald's host boot field. Sequence is an unsigned 64-bit canonical decimal string, incremented once at event creation, including filtered events, with exhaustion stopping admission. Hostname changes alter presentation only. Disk clones must regenerate machine identity before use; replacement boards get new identities. Duplicate claimed IDs from different peers remain separate selectable sources and raise a bounded diagnostic.

Origin UTC nanoseconds can be null; origin monotonic time, collector wall-clock receipt, relay wall-clock receipt, local journal receipt and journal cursor remain separate. A timestamp neither authenticates origin nor proves clock accuracy. UTC header precision is limited to six fractional digits; full origin nanoseconds remain in the MSG. Relays never substitute their hostname/time for the origin header.

Collector adds its stable ID, observed peer IPv4/port, configured peer slot, local receipt timestamp, ingress class and claimed relay data. Relay ID in a packet is a claim. USB validation binds a record to selected physical device and current boot but is not cryptographic authentication. IPv4 allowlists reduce exposure and do not authenticate UDP. No caller-supplied field may create journald underscore-prefixed fields or grant Fleet/controller authority.

Dedup key is `(ingress trust class, configured source slot, origin kind, origin ID, origin boot, sequence)`. Store at most 2,048 keys total, 64 per UDP peer, for 60 monotonic seconds; USB uses its separately bounded existing admission. Exact repeats in one ingress scope are suppressed. Conflicting content for one key is rejected and counted, never overwrites an accepted record. Direct UDP, forwarded UDP and physically checked USB remain separate scopes even if they claim the same origin; display related arrival paths instead of collapsing them. UDP cannot prepopulate or evict the USB cache. A spoofed packet can still poison its own unauthenticated peer scope: the UI must expose that limitation. Cache expiry/restart can allow duplicates again. Dedup is bounded noise reduction, not reliable delivery or an audit guarantee.

## UDP wire profile

Use [RFC 5424](https://www.rfc-editor.org/rfc/rfc5424.html) with [RFC 5426](https://www.rfc-editor.org/rfc/rfc5426.html): one complete message per datagram, no newline, NUL, USB prefix, length framing or application fragmentation. Set UDP checksums. The initial project profile caps the **entire UDP payload at 480 octets**. IPv4 and UDP headers add at least 28 bytes; 480 does not guarantee avoidance of fragmentation on every possible path. Respect a smaller discovered path MTU, count local size errors and drop rather than splitting events. IPv6 is deliberately unavailable: Pico `lwipopts.h` sets `LWIP_IPV6 0`.

The verbose USB JSON does not fit reliably inside 480 bytes. Introduce independent `wsprry-udp/1` MSG encoding, not a reinterpretation of `wsprry-log/1` or `usb-logging/1`. Header is `<PRI>1 TIMESTAMP HOSTNAME APP-NAME - MSGID - MSG`; facility is 23, severity is 0–7, APP-NAME is `WsprryPico` or `WsprryPi` for the origin, MSGID is the existing event code (1–32 printable ASCII characters excluding space, quote and backslash), and HOSTNAME is origin hostname (1–63 hostname characters or `-` for unavailable). TIMESTAMP is UTC with six fractional digits or `-`. The MSG is the following exact ten-element compact JSON array, with no optional trailing elements:

```text
["wsprry-udp/1",kind,origin_id,boot_id,sequence,utc_ns,monotonic_ns,dropped,message,relay]
```

`kind` is exactly `pico` or `pi`; origin/boot IDs are 32 lowercase hexadecimal characters. Sequence, monotonic and dropped are canonical unsigned 64-bit decimal strings; sequence starts at 1. UTC is null or a canonical unsigned 64-bit decimal string. Message is 0–192 printable ASCII characters. Relay is null for direct origins or the exact tuple `[relay_id,receipt_us,"usb"]`, with a 32-character lowercase hexadecimal relay ID and canonical unsigned 64-bit decimal-string receipt time. Only a Pi may relay; forwarded origin kind must be `pico`, and origin/relay/collector IDs must not conflict. Exactly one relay is permitted. Native Pi packets use null relay. No arbitrary JSON objects, extra elements, floats, booleans in numeric positions, duplicate fields, unknown tags or forward-compatible guessing are accepted.

Decode this tuple into the existing logical fields; obtain origin name, event, facility and severity from the strictly validated RFC header. Preserve relay observations separately. Require consistency between UTC header and the microsecond-truncated UTC value; NIL header requires null UTC. Reject malformed UTF-8, controls, BOM, truncated JSON, excess nesting, invalid RFC syntax, mismatched origin application/kind and excess size before journaling. The Pi collector accepts only this project profile initially, not arbitrary RFC 3164/5424 records. External collectors still receive a legal RFC 5424 MSG containing project JSON.

Before encoding, sanitize diagnostic text to printable ASCII using the existing replacement policy, escape JSON quote/backslash, then shorten **message only** until the whole datagram fits. Preserve all identity/time fields and valid closing JSON. Do not cut the serialized JSON or rely on receiver truncation. Native messages additionally pass an explicit export-safe event/text policy: exclude credentials, raw HTTP/configuration bodies, tokens, proofs, certificates and private support material; unsupported event classes are not exported. Regex replacement alone is insufficient. Add producer-owned journal fields for the export-safe event/template and allowlisted parameters in `src/logging.cpp`; never reconstruct approved text by treating arbitrary LCBLog MESSAGE content as safe. The worker exports only that validated projection, while local MESSAGE remains unchanged. Apply the same redaction gate before native or USB forwarding. Fixed event templates and allowlisted bounded parameters are the implementation acceptance rule.

Worst-case metadata with 63-character hostname, 32-character MSGID, full-width unsigned counters, maximum timestamp and a USB relay consumes 401 bytes including an empty message string; 79 serialized bytes remain for text. Escape-heavy text may retain only 39 characters. Shorter ordinary metadata leaves more room, capped at 192 original characters. A packet may legitimately carry an empty message; its event code still identifies the event. Truncation is counted locally; do not invent fields in the closed origin contract. Implement boundary vectors, including UTC representability: reject UTC values outside the RFC timestamp implementation's supported calendar range, even though the numeric container is unsigned 64-bit.

## Destination and sender lifecycle

Initial destination is an explicit dotted-decimal IPv4 unicast literal; DNS hostnames, mDNS and IPv6 are rejected with a useful validation message. This removes asynchronous DNS/cache expiry and rebinding from initial scope and avoids contention with Pico's one pending DNS request. No resolution state is advertised in this version. A future hostname feature needs its own explicit schema, bounded TTL/cache, retry and generation-bound callbacks; it is not latent behavior in this profile.

Accept ports 1–65535, recommend collector port 5514, and support externally configured 514. Reject unspecified, loopback, multicast, limited/directed broadcast, local interface addresses and the active collector's own listening endpoint. Reject noncanonical octets, suffixes, whitespace and extra address syntax. Revalidate against current interface addresses/subnet masks and routes on every network generation and before socket submission. Link-local unicast is permitted only on the explicitly selected local link; Pico uses station only, never setup AP. Unreachable unicast routes produce local failure or unknown receipt, never automatic destination replacement. Pi sender binds the selected interface and source address; no destination fan-out or fallback.

On link/profile/address/route generation changes, discard queued packets for the old generation, invalidate the PCB/socket and active destination, then rebuild after validation. No blocking network wait or retained packet pointer across a generation. Bound journal scanning to 32 entries per cycle as well as UDP receipt; skip rejected entries without emitting recursive per-entry diagnostics. IPv4 configuration and destination changes require authoritative saved-state application before new submissions; old queued text is cleared. Disabling export clears that sink only.

Proposed user settings are enablement, destination IPv4, destination port, maximum severity, event-code allowlist (empty means all export-safe events), events/second and burst. Default disabled, destination null, port 5514, severity 6, empty allowlist, rate 4 and burst 8. Enabled requires a destination; disabled may preserve a valid destination draft. Allowlist has at most 16 unique event codes of 1–32 safe ASCII characters. Pico rate is integer 1–8, burst 1–16; Pi aggregate rate is 1–64, burst 1–128, default 16/32. Rejected input does not normalize custom values or write anything.

States are `disabled`, `awaiting_network`, `invalid_destination`, `ready`, `submission_failed` and `unavailable`; API/frontend render these as configured/active distinctions. `ready` means locally configured, never collector receipt. Every successful `sendto` or lwIP submission means only local acceptance; receipt stays `unknown`. Counters distinguish generated, filtered, redacted/rejected, queued, overflow, expired, reconfigured drops, truncated, attempted, locally submitted and locally failed. Saturate counters at UINT64_MAX rather than wrapping. Sequence gaps include filtering, queue losses and restarts and cannot measure total network loss.

## Resource budgets and RF separation

Pico event creation must not be gated by USB enablement, DTR or stream permission. Assign one origin event ID, then independently filter/enqueue USB and UDP copies. Preserve existing USB queue/rate/disconnect behavior. UDP has its own 16 fixed-record queue, 480-byte formatter and one datagram submission per core-0 poll, at most eight per second. Expire records after five monotonic seconds; overflow drops newest. No retries of failed datagrams; token buckets prevent outage recovery bursts. No heap allocation in event admission, formatting or polling; no IRQ/core-1 calls, flash writes, blocking DNS, waits or per-symbol logging. Proposed incremental UDP object ceiling is 8 KiB plus one lwIP PCB/pbuf; link-map and stack/pool audits must prove fit before acceptance. Increase `MEMP_NUM_UDP_PCB` from six to seven only with simultaneous AP DHCP/DNS, station DHCP/DNS, mDNS and NTP pool-pressure tests. Do not borrow the NTP PCB or claim current pools already suffice.

Pi service budgets: 256 pending outgoing datagrams, five-second expiry, 16 sends and 32 received datagrams per 50 ms cycle, 480-byte inbound cap with oversize/truncation detection before parsing, 32 configured peers, 64 dedup slots per peer and 2,048 total. One peer gets at most eight accepted records/second with burst 16; aggregate journal admission is 128/second with burst 256. Round-robin admitted peer queues have eight records each, newest-drop overflow and five-second expiry. Drop unknown peers before JSON work; bound total receive attempts to 32/cycle so spoofed floods cannot create unbounded parser work. Fixed receive-buffer size is 64 KiB; process memory ceiling is 32 MiB and two worker threads, enforced by service limits. DNS workers are absent. Kernel UDP drops and journald rate-limit drops are separate from application counters. Sustained floods may deny logging but cannot block transmitter loops.

## Pi service, persistence and Logs projection

Install the separate MIT-owned executable and disabled-by-default `wsprrypi-log.service`; no rsyslog replacement, firewall opening or listener activation during upgrade. Use static system user `wsprrylog`, no root, no device access, no transmitter IPC, `NoNewPrivileges`, empty capability bounding set, read-only system/home restrictions and address-family restrictions to AF_INET/AF_UNIX. Its supplementary journal-read group is broad host-journal access; expose that privilege in installation/support documentation and minimize reader filters. Do not give that group to the UDP sender UI. Policy is root-owned and readable by the logging user; the existing authenticated host control path atomically writes it. Service notices a revision change through a bounded local notification/poll; it cannot write arbitrary host files.

Default listener binds one explicitly selected interface's IPv4 on 5514; no wildcard bind. Port 514 reception uses an explicitly installed systemd datagram socket passing the already bound fd to the unprivileged worker; no executable ambient capability and no root worker. Missing/conflicting socket, interface or policy reports unavailable. Socket and service policy generations must agree before receipt; changing bind/port has a visible brief interruption and uses the controlled service-management path. Validate before stopping the old listener. No automatic takeover of port 514 from another daemon.

Proposed policy file `<ini>.udp-logs.json` is independent of `<ini>.usb-logs.json` and native INI. Exact schema `host-udp-logging/1` contains schema, collector_id, revision, sender and collector; sender additionally contains `native_enabled` and `usb_sources` (at most eight exact saved Fleet profile/device pairs). Collector contains `enabled`, `bind_ipv4`, `interface`, `port`, `peers`; peers are up to 32 unique `{slot,ipv4}` entries, slot matching `[A-Za-z0-9_-]{1,32}`, with no wildcard/subnet admission. Empty peer list admits nothing. No remote-origin ID in this policy grants authentication. All policy arrays are unique and strictly bounded. Save via temporary file, fsync, atomic rename and directory fsync; apply only fully validated revisions. Corruption disables UDP, never rewrites the policy or chooses an older enabled policy. Stop removes sockets/queues within five seconds; restart is rate-limited and starts with empty volatile queues. Removal disables socket/service and preserves policy for deliberate operator deletion. Installed status must distinguish missing binary, inactive service, invalid policy, bind error and ready.

Imported records enter the real `wsprrypi-log.service` journal with custom `WSPRRY_*` origin/provenance fields and normal MESSAGE/PRIORITY/facility; never fabricate `_SYSTEMD_UNIT`, `_HOSTNAME`, `_BOOT_ID`, `_PID` or receipt cursors. The current SSE adapter filters `wsprrypi.service` and would hide these imports. Keep the old endpoint unchanged. Add an explicitly selected Logs stream version 2 with a fixed OR of the two trusted service units, including required systemd manager lifecycle messages only through their existing verified manager rule. Update both journal query construction and `log_scope_matches`, cursor membership tests, replay, follow and normalization. Do not widen to arbitrary units, `unit=*` or trust an unprivileged payload's unit field. Support package permissions and journal visibility must be verified for the new unit.

Version-2 events retain current journal/SSE fields and add explicit source scope, observed peer slot/address, ingress trust, claimed origin, relay tuple and nullable origin data. Unknown or missing remote origin must never fall back to the collector's host identity; current `log_origin.php` defaults must be separated by trusted unit/ingress. `local` means this Pi's native origin, not every non-Pico record. Source keys are `local`, `usb:<device-id>`, `udp:<peer-slot>:<kind>:<origin-id>`, or `all`. Treat direct and relayed arrivals as distinct ingress subfilters within a peer. Bound selectable history to the configured 32 peers and 64 recently observed origins per peer; extra origins can appear in All with a bounded overflow warning, not an unbounded source menu.

## Versioned management and compatibility

Introduce independent authenticated discovery at `/api/v1/udp-logging/capabilities`, schema `udp-logging-capabilities/1`, rather than adding fields to any existing closed descriptor. Exact top-level fields are `schema`, `target`, `resource`, `settings_schema`, `wire_schema`, `limits`. Target is the existing exact member scope/device_id/boot_id binding on Pico, or host scope/collector_id on Pi. Resource is the fixed settings path below; settings_schema is the exact applicable schema; wire_schema is exactly `wsprry-udp/1`. Limits has exactly `payload_bytes`, `queue_records`, `maximum_sources`, `maximum_peers`, `maximum_rate`, `maximum_burst`, `address_family`; values match this proposal (Pico sources/peers zero, Pi sources eight/peers 32; IPv4 only). Unknown/mismatched versions or limits refuse management before writes. Older peers return unsupported/404; never infer support from firmware version or an existing USB logging advertisement.

Pico settings: `GET/PUT /api/v1/udp-logging`, independent `transmitter-udp-logging/1`. PUT has exactly `schema`, existing exact member `target` and `settings` with the sender keys specified above (`enabled`, `destination_ipv4`, `destination_port`, `maximum_severity`, `event_codes`, `rate`, `burst`). GET has exactly `schema`, `target`, `saved`, `active`; ETag is in the HTTP header. Pi host settings use `/api/v1/host/udp-logging`, schema `host-udp-logging/1`, exact host target and the host sender/collector policy above. Stored revision/collector binding is supplied by the host service, never accepted from a packet. PUT requires exact target, If-Match and authenticated mutation context; saved and active remain distinct. Active has exactly `state`, `applied_revision`, `receipt` (`unknown`), `queued`, `counters`; counters use the names enumerated above as decimal strings, and Pi uses the host active shape below. Encode these proposed shapes as closed schema files with no additionalProperties; do not improvise new wire versions in code.

### Exact host resource and active shapes

The on-disk host policy is exactly `{schema,collector_id,revision,sender,collector}`. Its API PUT is exactly `{schema,target,settings}`, settings exactly `{sender,collector}`; its GET is exactly `{schema,target,saved,active}`, saved exactly `{sender,collector}`. Schema is `host-udp-logging/1`; target is exactly `{scope:"host",collector_id}`. Revision is an opaque nonempty 1–128-character printable ASCII token generated by the host and carried as ETag/If-Match; it is not a JSON number. Host sender has the seven common sender settings plus `interface` (1–15-character existing interface name), `native_enabled` boolean and `usb_sources`. Each USB source is exactly `{profile_id,device_id}` matching the existing saved Fleet profile and device ID without new profile syntax. A source must already be collected through the separately enabled USB policy; selection does not enable it. Collector interface uses the same bound; bind_ipv4 is null only while disabled, port 1–65535 defaults 5514. Collector defaults disabled, null bind, empty peers and the chosen explicit interface. Missing interface is represented as null while disabled only; enabled send/listen requires an existing explicit interface. Unavailable/removed saved profiles remain visible for removal but cannot be newly admitted or forwarded.

Host active is exactly `{applied_revision,sender,collector}`. Sender is exactly `{state,receipt,queued,counters}`, with the same sender states/counters as Pico, queue integer 0–256 and receipt `unknown`. Collector is exactly `{state,bind_ipv4,port,counters,peers}`; state is one of `disabled`, `awaiting_network`, `ready`, `bind_failed`, `unavailable`, `policy_invalid`. Bind/port are the actual current values, null when not bound. Counters has exactly `received`, `oversize`, `disallowed`, `malformed`, `duplicate`, `conflict`, `limited`, `overflow`, `journal_failed`, `journal_submitted`, `discontinuity`, all canonical saturating unsigned 64-bit decimal strings. Peers is an array of at most 32 entries each exactly `{slot,received,last_receipt_us}`, matching configured slots; received is a decimal counter, last_receipt_us null or canonical unsigned 64-bit decimal string. Global invalid/disallowed traffic gets no dynamic peer object. `applied_revision` is null if none has applied, otherwise the opaque ETag token. Pico active queue is integer 0–16; its applied_revision has the same nullable token rule. All `settings.enabled`/policy selection flags are JSON booleans; all ports/rates/bursts/severities are bounded JSON integers, never strings/coerced booleans. Destination IPv4 is null or the validated literal; origin identifiers and allowlist constraints remain exact. Common counters has exactly `generated`, `filtered`, `redacted_rejected`, `queued`, `overflow`, `expired`, `reconfigured_drops`, `truncated`, `attempted`, `locally_submitted`, `locally_failed`; counters.queued is cumulative admissions, active.queued is current occupancy.

Capabilities limits.queue_records is 16 on Pico and 256 on Pi; maximum_rate/maximum_burst are 8/16 and 64/128 respectively. Resource is `/api/v1/udp-logging` for a Pico and `/api/v1/host/udp-logging` for a Pi. Maximum_sources/maximum_peers are zero on Pico. Address_family is exactly `ipv4`. Capabilities target uses the same exact binding as the settings API. API body size ceilings are 2 KiB Pico and 16 KiB host; parser depth is at most eight. Do not fetch fields until shape/type/duplicate-key checks pass; reject unsupported methods, schemas, carrier claims, noncanonical numbers and mismatched advertised limits before mutation. Host disk schema additionally validates its stored binding/revision and never accepts API target fields as peer claims.

The selected-member Pi proxy is `/api/v1/member/udp-logging` plus its matching capabilities proxy. Extend the existing USB and authenticated network bridges with exact selected device/boot/profile/selection/revision binding and resource allowlists. A USB selection cannot become network authority; a network selection cannot claim USB physical authority. Both carriers must exercise this same resource. Support consumer sessions and engineering authentication using their existing lifetime limits; no WTP job or session-policy change is needed. Keep existing capability endpoints, application views, `transmitter-management/1`–`/5`, USB logging and historical limits unchanged. If implementation needs to change a closed descriptor anyway, introduce and pair-test a new explicit version before shipping, rather than silently extending it.

Pico persistence uses a **new independent UDP journal format**, proposed `udp-logging-state/1`, in two 4 KiB sectors at `[0x3ec000,0x3ee000)`, immediately below the existing NTP region. Reduce `linked_flash_size` from `0x3ee000` to `0x3ec000`; add static adjacency assertions and update every linker/image bound, bundle manifest, firmware writer, reset/erase path and paired installer validator together. This is a selected new reservation, not a claim that current images already fit. Reuse the two-bank CRC journal with 2,048-byte records and 1,984-byte payload limit; the exact UDP settings object plus its schema envelope fits under 1 KiB even with sixteen maximum-length event codes. The journal envelope has exactly `schema` and `settings`. Reject a candidate image reaching the reserved region. Do not move any existing persistent region or redefine standalone-state/4. The installed/developer bundle must declare the new application end `103ec000` through an explicitly new storage/update contract and matching versioned manifest/local-build schemas; retain exact contract-1 handling of its historical ends. Update `scripts/ci/bundle.py`, its manifest schema, `scripts/usb_installer.py`, image audit scripts and Pi maintenance/bootstrap bundle validators together, including same-board installed-bundle reconciliation. An old installer must refuse the new bundle, and a new installer must validate historical/current bundles with their own limits rather than accepting an arbitrary address range. This proposal selects update contract 2 for the new layout; USB command framing and postboot verification retain their independently versioned meanings. Rollback images must also end below `0x3ec000`; otherwise refuse rollback until a reviewed, settings-preserving migration exists. All unrelated saves preserve UDP policy; erasure/reset behavior is explicit (factory reset clears it; ordinary restart and settings-preserving upgrade retain it). Unsupported/corrupt UDP journal disables UDP without restoring older enablement. Before downgrade, save disabled/read back, retain recovery bundle and validate the older firmware's handling of that region. Never offer an erase as automatic rollback. Future ordinary firmware deployment uses the shared USB installer, retained developer bundle, same-board reference and postboot verification.
