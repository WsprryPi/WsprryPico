# UDP logging

UDP logging exports selected Pico and Pi events to one IPv4 unicast destination. Export and collection default off. Direct Pico export, native Pi export and forwarding selected USB Pico records are independent settings. A collector need not control a transmitter. Imported UDP records never forward to another collector.

Pico UDP settings and descriptors use stable `udp-logging` and `udp-logging-capabilities` types within `Wsprry-Control/1`. The UDP event wire `wsprry-udp/1` and Pi host policy `host-udp-logging/1` remain independent. USB logging carriers, Consumer-Radio sessions and WTP command formats retain their separate authority. The shared [portable codec](../../src/logging/udp_wire.hpp) and fixed event policy are mirrored in Pi and Pico source; their fixtures exercise the actual selected sources.

## Wire profile and trust

Each datagram contains one RFC 5424 message using RFC 5426 transport, with no USB framing, newline, NUL or application fragmentation. The entire UDP payload is at most 480 bytes. Only message text can be shortened to fit; identity and metadata are retained. The header uses facility 23, severity 0–7, origin hostname or `-`, application `WsprryPico` or `WsprryPi`, PROCID `-`, the event code as MSGID and structured data `-`. Header UTC uses six fractional digits or `-` when unknown. Full origin UTC remains independently nullable in the message.

MSG is the exact ten-element array defined by [wsprry-udp/1](../protocol/wsprry-udp-1.schema.json):

```text
["wsprry-udp/1",kind,origin_id,boot_id,sequence,utc_ns,monotonic_ns,dropped,message,relay]
```

`kind` is `pico` or `pi`; origin and boot IDs are 32 lowercase hexadecimal characters. Sequence is positive; sequence, monotonic nanoseconds and origin drop count use canonical unsigned 64-bit decimal strings. UTC nanoseconds use the same decimal representation or null. Message text is at most 192 printable ASCII characters before payload-size truncation. Relay is null for direct export, or `[relay_id,receipt_utc_us,"usb"]` for one USB relay; the relay ID is a distinct 32-character identity and receipt time is a canonical unsigned decimal string in microseconds. A Pi-origin event cannot carry a relay. Unknown versions, extra tuple elements, malformed counters, inconsistent header/tuple identity or time, invalid relay and overlength messages are rejected.

UDP is plaintext and unauthenticated. An IPv4 allowlist does not authenticate claimed origin, relay, hostname or time. A collector records observed peer and receipt information separately from payload claims. Direct UDP, forwarded UDP and verified physical USB have separate ingress scopes; an unauthenticated UDP claim cannot suppress a verified USB record or grant transmitter authority. Sequence gaps and local-send counters do not establish where a datagram was lost.

## Sender and collector lifecycle

Pico settings select a literal IPv4 address, destination port, maximum severity, event-code filter, rate and burst. Defaults are port 5514, severity 6, rate four events per second and burst eight. The supported ranges are ports 1–65535, severity 0–7, rate 1–8, burst 1–16 and at most sixteen unique event codes of 1–32 allowed ASCII characters. An enabled sender requires a valid destination. DNS, IPv6, multicast and broadcast export are unavailable; the station adapter also rejects local or unsuitable routed destinations. Port 514 is supported as an explicit destination. These bounds are defined by the [current control schema](../protocol/control-1.schema.json), its capability descriptor and production adapter.

Pico event creation assigns one origin sequence and snapshots the cumulative origin drop count before independent USB and UDP admission. A delayed USB delivery retains that snapshot; the live USB status counter continues to report subsequent USB losses. The UDP sink has sixteen fixed records, a five-second lifetime, separate filters and token bucket, and a hard ceiling of eight submissions per monotonic second. Its core-0 station adapter owns a distinct IPv4 PCB and a bounded pool buffer. Network generation changes invalidate queued events. A submitted datagram has unknown receipt.

The dedicated Pi worker reads only the real `wsprrypi.service` journal and emits imports under its own real `wsprrypi-log.service` unit. Export requires matching local collector identity, native or verified USB ingress, selected USB profile/device binding where applicable, and producer-owned fixed export templates. Unknown native event classes and arbitrary MESSAGE bodies are excluded. UDP imports and worker diagnostics never forward. No UDP payload supplies trusted underscore-prefixed journal metadata.

Routine Pico WTP and Management port transitions use `USB_STATE` at DEBUG severity 7, with fixed text identifying the port and opening or closing. Default severity 6 excludes them. Direct Pico export and Pi forwarding admit the same four templates and retain the historical generic message for older firmware. Event schemas, carrier versions and settings limits are unchanged.

The verified Pi executable embeds the separately built logging worker. Installation extracts and compares that image before installing the dedicated executable and hardened static-user service. Existing precompiled application images without the worker retain disabled UDP policies and report the feature unavailable; an enabled policy refuses such a downgrade. Installed host logging stacks and firewall rules remain unchanged. The logging user's supplementary journal group grants broad host-journal read access; it does not grant device or transmitter authority.

Pi sender policy can select native events and up to eight saved USB profile/device pairs; collector policy admits up to 32 unique IPv4 peer slots on one explicitly selected interface/address. Empty peer lists admit nothing. The Pi queue is bounded to 256 records; its sender rate/burst ceilings are 64/128. Port 514 collection uses a managed systemd datagram socket that passes its descriptor to the unprivileged worker. Bind conflicts refuse policy changes; existing host logging daemons and firewall rules remain under their own administration.

Host policy is stored independently in `<ini>.udp-logs.json`. Settings discovery and resources are `/api/control/v1/udp-logging/capabilities` and `/api/control/v1/udp-logging` on Pico, and `/api/control/v1/udp-logging/capabilities` and `/api/control/v1/host/udp-logging` on Pi. The closed capability descriptor binds the exact settings schema, wire schema, limits and selected target. Saves require authentication, exact target and revision, with authoritative readback after an uncertain reply. Configuration merges, USB logging and unrelated saves preserve the independent UDP policy. Pico UDP documents use an eight-level parser budget. Root control mutations require `contract:"Wsprry-Control/1"`.

Logs stream version 2 selects the two trusted service units and carries explicit origin, peer and ingress provenance. Remote Pi records remain distinct from the local Pi, and direct/relayed arrivals have separate source filters and cursor contexts. Journal cursors are separate from producer sequence and receipt time. Replay/follow and view pause do not enable export or collection. General support output excludes private UDP message bodies.

## Independent finite test resource

Test-event discovery is independent of settings discovery. `GET /api/control/v1/udp-logging/test/capabilities` on a Pico and `GET /api/control/v1/host/udp-logging/test/capabilities` on a Pi expose their closed test descriptors. The Pico discriminator is `udp-logging-test-capabilities` within the shared control contract; the independent Pi host discriminator remains `udp-logging-test-capabilities/1`. It contains `schema`, exact settings `target`, `resource`, `request_schema`, `event_code` and `maximum_rate`. The Pico request schema is `udp-logging-test`; the independent Pi host request schema is `udp-logging-test/1`. The maximum rate is two requests per second, and the event code is `UDP_TEST` on Pico or `PI_LOG` on Pi. Unknown descriptors disable testing without guessing an older diagnostic resource.

The corresponding test resource accepts only authenticated `POST` with exact `{contract,schema,target}` on Pico and the authoritative settings If-Match revision. It checks identity, revision, idle admission where applicable, enabled export and the event/severity filter before admitting one fixed diagnostic event. It does not write settings or flash, submit a radio job, acknowledge a collector or retry automatically. The Pico reply is `{contract,schema,target,accepted,receipt}`, with boolean local admission and receipt `unknown`. The member proxy uses the same selected-device, boot, profile, carrier and revision guards as settings. The UI offers testing only after saved-state readback and independent diagnostic discovery.

## Storage and bundles

The independent UDP settings journal occupies `[0x3ec000,0x3ee000)`, leaving existing regions fixed. Current application images end at `103ec000`. Release manifest 2 and developer bundle 2 declare storage/update contract 2 explicitly; old manifest and developer bundle 1 retain their own exact historical ends. Developer bundle 2 supports explicit normal and inhibited engines, keeps the retained image filename stable, and validates linked engine identity. The shared installer hashes the actual source inputs and retains the exact bundle and same-board reference through postboot verification.

New transactions preserve the selected layout's reserved region. Historical installer receipts retain their original NTP-inclusive preservation hash boundary. A contract-2 application cannot be replaced by an image whose application reservation expands into the UDP journal; a reviewed settings-preserving migration is required. No erase or deletion of a same-board reference substitutes for that migration.
