# Phase 05 Adopt the qualified browser lifecycle

Execute only phase 05 when explicitly invoked. Read the complete
[shared execution contract](README.md#shared-execution-contract),
[orientation](orientation.md), and accepted evidence through phase 04. Do not
migrate other suites until the pilot's lifecycle, selection, sensitivity, and
both-carrier checks pass. Pending remote settings approval remains separately
visible rather than weakening these gates.

## Objective and scope

Apply the accepted pilot pattern to every maintained software browser entry
point while preserving scenario/context independence. Inspect the current
session-timeout, submission, sections, recovery, standalone-frequency, hostname,
organization, WSPR, and message-frequency runners, plus already-improved progress
and operator-cleanup runners, imported UI helpers, and the shared fixture server.
Inventory opt-in field and hardware entry points separately; do not execute or
retire them incidentally. Do not redesign product UI or parallelize suites here.

## Work

1. Build a caller/context matrix before editing: suite, arguments, definition
   profiles, carrier, browser contexts, fixture resets, shipped/source assets,
   imports, output/capture controls, dialogs/popups, and required assertions.
   Distinguish the message-frequency runner's two surfaces from two separate
   command invocations, and preserve both section carriers.
   Count actual browser launches, driver launches, command invocations, and
   logical contexts separately; a loop inside one command can launch more than
   one browser and is not evidence that a context disappeared or was duplicated.
2. Adopt one bounded startup/CDP/operation/cleanup pattern. Bound discovery,
   connection opening, response body reads, request correlation, dialog/target
   handling, cancellation, early socket/process exit, and finalization. Preserve
   diagnostics and nested remaining budgets. Restrict retries to identified
   transient states; assertion, malformed-protocol, and programming errors must
   not be repeatedly swallowed until a generic timeout.
3. Select only the profiles each invocation actually uses. Reverify the earlier
   seven-invocation, seventy-start, eight-used-profile calculation. Keep stable
   profile/authority/port mappings, current explicit opt-in contexts, and required
   fixture reboot/replacement behavior. Never reuse authenticated sessions or
   mutable journals across suites to save startup time.
4. Consolidate duplicated plumbing only where semantics match. Charge extracted
   code and all adapters. Shared code must not execute a suite on import or
   silently replace an oracle. Preserve source-versus-shipped coverage, real
   crypto/handlers, keyboard/accessibility checks, viewport/overflow assertions,
   saved drafts, files, History, lost replies, and cancellation. A no-capture
   option must not acquire new power to skip assertions.
5. Keep deliberately observed cold startup and helper failure regressions. Do not
   replace the real delayed-start stimulus with only a fake-clock unit test.
   Reconcile every migrated consumer of phase 03/04 interfaces and phase 02
   completion evidence. Leave scheduling changes to phase 09.

## Validation and adversarial assessment

Run every affected suite/context from the matrix, shared lifecycle regressions,
and both actual production network and USB suites for the intended source pair.
Cover session-isolation and profile-routing defects, delayed/partial discovery,
stalled open/request, reordered replies, popup disappearance versus real CDP
error, changed boot, fixture replacement, and primary plus cleanup failure.
Confirm each invocation's expected scenario completion and owned-process count.
Prove representative deliberate product defects are still detected after helper
extraction. Restore sensitivity changes before final verification.

Challenge selective startup for silent carrier loss, context aliasing, changed
capture/assertion behavior, catch-all retries, and uncharged helper/regression
cost. Fix findings, rerun affected checks, and reassess. Repeated happy-path passes
do not substitute for these checks.

## Acceptance and handoff

Deliver a reconciled before/after context map with no required losses, observed
startup/process counts including added regressions, source-pair evidence, and
separate code/file/runtime budgets against phase 01. Report seventy-to-eight only
if current evidence supports that exact submetric; never label it whole-CI saving.
List any genuinely distinct helper exceptions with rationale. Update phase status
only after all required checks pass and hand resource ownership/port constraints
to phases 06/09, then stop.
