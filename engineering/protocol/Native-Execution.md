# Native execution and output safety

Each device owns its recurring schedule and executes locally. A Pi uses its explicitly selected native backend; a Pico uses its standalone scheduler. Management configures and observes the selected device. It does not upload finite jobs or dispatch occurrences to another transmitter.

## Internal execution contract

The Pico scheduler submits typed, bounded requests to the existing JobService and engine. Internal `wtp` types and namespaces remain implementation details; they are not a supported external protocol. A request is immutable and belongs to one full device/boot/owner context. Names, catalog handles, and connection state do not establish identity or authority.

The shared event profile uses integer nanoseconds and integer nanohertz. Events start at offset zero, have positive durations, remain contiguous and ordered, and exactly fill the declared duration. RF-on events specify a positive frequency; RF-off events omit it. Arithmetic must fit unsigned 64-bit bounds. Validate event count, complete duration, supported mode, engine range, and realization policy before admission. The current Pico execution descriptor supplies the actual bounds, including the 512-event ceiling and smaller configured duration limits. Never truncate, split, stretch, or silently substitute an unsupported request.

Frequency placement belongs to the native producer. Pi WSPR derives RF center from dial plus 1,500 Hz and one per-plan random placement; both frames of a paired plan retain that placement. Pico standalone produces its own native grid. An accepted absolute event receives no second dial offset or host calibration. Requested frequency, engine realization, and measured RF remain separate observations. Device calibration does not authorize changing an immutable accepted request.

## Ownership and terminal state

All local producers share one exclusive ownership service. A management disconnect or expired session cannot retime armed or running execution. Ownership remains through terminal handling; release preserves retained observations. A loaded request can be cancelled, but release is refused while armed, running, or in an unresolved output fault. Foreign ownership cannot be taken over by schedule configuration or stop through an unrelated management context.

The engine progresses through empty, loaded, armed, running, and complete/aborted/missed/failed observations. Completion and cancellation command output off and require bounded confirmation. Failure to confirm inactive output latches failed/unknown; a terminal state alone is never proof that output is inactive. New admission and authority release require the appropriate confirmed inactive state. Only local engine recovery can clear a failed output latch after verifying inactive output.

Retries cannot turn a retained terminal request into another execution. Internal request/job identities and content bindings prevent conflicting reuse. Retained results are bounded; absence or expiry of an observation does not establish successful completion. Unknown work stays held without load/arm replay.

## Clock admission and launch

Management and time provisioning remain available without qualified UTC. Execution independently requires the current clock state, uncertainty, holdover age, minimum lead, horizon, and leap policy. All interval arithmetic is checked. Unknown leap state and overlap with the exclusion window around a pending leap transition refuse admission.

An accepted UTC start remains immutable. Before launch, the device may refine its monotonic mapping using a newer admissible clock sample, within the original deadline. It rechecks clock validity and uncertainty before enabling output. It never deliberately starts early. A delayed launch must precede the exclusive end of the UTC second containing the requested start; this is not a rolling one-second allowance. A missed deadline leaves output disabled and does not retry the occurrence. Timer quantization rounds upward within that same second. Once running, the complete event sequence uses monotonic timing; UTC correction or loss of synchronization does not alter its duration.

Console launch counters are implementation diagnostics, not electrical edge measurements. Read current authenticated status for ownership and output observations. Software fixtures qualify these contracts only, not hardware timing, frequency accuracy, GPIO, services, installation, or RF.

## Native schedule stop

Authenticated GET/POST `/api/control/v1/schedules/stop` reads or stops both Pico native schedules. A mutation binds the current full device/boot target and exact revision, requires current authorization, uses one explicit POST, and returns confirmed disabled, inactive, unowned state. It uses the existing engine cleanup path and preserves settings, recurrence cursors, and recovery records. Persistence failure remains held; a foreign owner or unresolved output refuses success.

A lost response is unknown. Preserve drafts and use explicit stop-status readback from the same target before another action; never replay a stop mutation automatically. Ordinary status refresh does not resolve an uncertain stop. Local USB Console STOP remains a separate trusted safety control with its existing restart-cleared behavior. Re-enabling after native stop requires an explicit current settings read and deliberate native enable.

## Authenticated finite Test Tone

The optional `test_tone` capability describes one finite, steady tone on the active Direct GPIO or Si5351 engine through authenticated Control/1. Engineering HTTPS, authenticated Consumer-Radio requests on station/AP, and local USB use the same coordinator and native executor. Public observer reads and plaintext consumer HTTP grant no tone operation. The capability's `available` field identifies an attached admitted engine; it does not grant Start admission. Each Review and Start checks current activity and policy. Arbitrary event uploads, client launch times, scheduling, repeats, queues, per-tone drive overrides, and an HP-side adapter are outside this resource.

The current contract remains `Wsprry-Control/1` under `/api/control/v1`; there are no resource version increments, historical settings views, or new persistent records. The canonical closed requests and responses are in [control-1.schema.json](control-1.schema.json). The Pi controller gateway route subset is unchanged; this is a Pico client API, and Pi integration is separate.

| Operation | Method and path | Conditional authority |
| --- | --- | --- |
| Review | `POST /api/control/v1/test-tone/review` | Authenticated current device/boot; no write precondition |
| Start | `POST /api/control/v1/test-tone/start` | Review's current `assessment_revision` in `If-Match` |
| Status | `GET /api/control/v1/test-tone/status?device_id=...&boot_id=...&request_id=...` | Same authenticated authority generation; alternatively select `job_id` |
| Stop | `POST /api/control/v1/test-tone/stop` | Identified job's `control_revision` in `If-Match` |

Status requires exactly one request-ID or job-ID selector and both identities. IDs are 32 lowercase hexadecimal characters. Query keys cannot repeat, and unknown keys, percent encoding, alternate target spellings, and ambiguous selectors refuse. Only this bounded Status query is admitted by HTTP, encrypted consumer, and USB routing; other routes retain their query restrictions. Consumer requests carry their normal encrypted logical request, including `if_match`; physical USB uses its existing management framing/ACK. No new authentication or transport version is introduced.

A Review request contains exactly `contract`, `schema: "test-tone-review"`, `target`, and `tone`. The target is the usual `{ "scope": "member", "device_id": "...", "boot_id": "..." }`. The tone contains the required engine assertion (`"pio-dma-gp2"` or `"si5351"`), integer `carrier_hz`, integer `duration_ms`, and `proposed_drive_ma`. Direct GPIO accepts 2, 4, 8, or 12 mA; Si5351 accepts 2, 4, 6, or 8 mA. The assertion must match the immutable boot engine and cannot select hardware. For example, `{ "engine": "pio-dma-gp2", "carrier_hz": 5366200, "duration_ms": 12000, "proposed_drive_ma": 4 }` assesses exactly 5,366,200 Hz. No WSPR offset, dial conversion, random placement, or saved-frequency substitution applies.

Review returns `ready`, `requires_restart`, or `refused`, bounded machine-readable reasons, the current assessment revision, effective maximum duration, proposed/saved/boot drive, RF pin, prospective launch, numerical realization, and clock assumptions or a native clock error. Proposed drive and a drive-only sticky restart latch do not prevent numerical prediction. Other pending hardware changes and faults remain explicit refusals. Review does not CLAIM, LOAD, ARM, freeze calibration, reserve output, prepare filters/SDK hardware, restart, or write configuration. Ordinary native background polling may still complete previously accepted work. Review is a snapshot, not a reservation.

The requested duration is 1–120,000 whole milliseconds for Direct GPIO and 10–120,000 ms for Si5351, further bounded by native and engine limits. The capability advertises exact engine-specific drive sets and verification bases, with the active engine and effective duration bounds separately reported. A smaller native ceiling is floored to milliseconds and advertised as `maximum_duration_ms`; requests are refused rather than clamped. Clock horizon, leap, and other admission checks can refuse a shorter tone. The capability separately advertises native output-disable timeout. These limits do not characterize meter settling or physical time accuracy. The RF interval excludes preparation, amplifier lead, normal amplifier tail, and shutdown confirmation.

Start uses `schema: "test-tone-start"`, the same current target, a unique `request_id`, and `tone` with the required `engine` assertion, `carrier_hz`, `duration_ms`, and `expected_drive_ma`. The drive is an assertion about immutable boot hardware, not a hardware-setting command. Start refuses if either native WSPR or message schedules is saved enabled, including suspended/ineligible schedules; output is owned, loaded, armed, running, or faulted; settings require restart; maintenance/recovery is pending; storage is unhealthy; or any native frequency, correction, filter, clock, lead, horizon, memory, or pin rule fails. It does not require complete station metadata merely to use a valid existing boot drive.

Acceptance consumes a nonreused boot-local admission sequence included in the global revision without a journal write. Start reserves a receipt, compiles one native `tone` job with one RF-on interval, privately claims native ownership, prepares through the frequency-policy engine, chooses a near-term device launch, and ARMs it. Native ARM rechecks its actual clock. The return is a `test-tone-status` document, normally HTTP 202, identifying accepted, running, or already terminal work. A partially accepted failure remains an identified terminal result with its native error and confirmed/unknown shutdown evidence. Refusal before native admission has no new runnable job. An accepted launch is not automatically retimed or retried.

The local RF worker and selected engine timeline ends the interval independently of HTTP, USB, login survival, ACK delivery, or caller polling. The coordinator uses the existing maximum 60-second native lease. Armed/running work retains exclusive output after lease expiry and settles through native shutdown before release; a 120-second tone does not require a lease extension or client renewal. Faults preserve native inhibition and ownership rules. No Test Tone resource clears a fault.

Start and Status return the same bounded job representation: immutable accepted request/job identity, absolute carrier and duration, accepted configuration/admission revision, RF pin or synthesizer output/reference/profile, boot-active drive, frozen correction/realization, scheduled/observed times where available, native state/error, phase, terminal outcome, and shutdown confirmation. `accepted`, `running`, and `terminal` are distinct phases; terminal outcomes are `completed`, `stopped`, `missed`, and `failed`. Nullable observations mean unavailable evidence. `observation_monotonic_ns` timestamps the separately labelled `current` device snapshot; that snapshot includes current saved/boot drive and current ownership/output. Saved drive remains null when no authoritative saved settings supply a value; the boot default is not substituted for it. An old job's inactivity never describes a successor. Direct jobs carry SDK `pad_readback` and null `synthesis_readback`; Si5351 jobs carry fresh epoch-bound `synthesis_readback` and null `pad_readback`. Si5351 realization reports null NCO increment and nominal sample clock. `inactivity_basis` distinguishes native GPIO shutdown from Si5351 register shutdown. Register confirmation is not an RF detector: a failed bus can leave physical output active and must report unknown/recovery, never successful shutdown.

The per-job `pad_readback` is an initialization-stage SDK register observation with execution epoch and monotonic timestamp. A fresh verification occurs on the RF owner for each execution epoch, before RF launch. The job's accepted RF pin and expected boot drive must match this observation; a mismatch or missing required verification aborts admission. Cached pre-ARM drive observation may be null and does not itself refuse Start. Each retained receipt owns its copy; neither a preceding nor a successor's observation is substituted. This is register verification, not measured current, RF power, or continuous electrical monitoring. Numerical frequency realization applies manual/GPS correction once and reports nominal clock, NCO increment, programmed nHz, correction generation, and half-step/integer-report rounding bound. Physical oscillator uncertainty and measured RF remain separate.

Stop uses `schema: "test-tone-stop"`, current target, and exact `job_id`, with that job's control revision. The revision is stable through accepted/running progress and changes when the job settles; repeated terminal Stop also accepts the original active revision to reconcile a lost reply. Global settings changes do not invalidate an otherwise correctly bound job Stop. Immediately before native job-specific ABORT, the coordinator compares its private owner and the native job ID. A stale Stop returns its retained terminal result without touching a successor. A terminal Stop response is successful shutdown only when `output_inactive_confirmed` is true. An unresolved shutdown reports false and `recovery_required`, preserves the native fault, and blocks subsequent Start even after lease or metadata expiry. Stop is synchronous and bounded by native shutdown; there is no separate asynchronous stopping queue.

Receipts are volatile and boot-scoped. At most eight settled receipts are retained for up to one hour; capacity can evict them sooner. Active or unresolved-fault work is pinned separately. An identical retained Start with the same original revision and typed content returns its existing job without native replay; changed content or original revision yields `request_conflict`. The consumed admission sequence prevents an old accepted conditional request from executing again after receipt eviction, including across settings changes. Sequence exhaustion refuses admission. Receipt absence returns `receipt_unavailable`, not proof that nothing ran. A changed boot refuses the old target and discards volatile records.

Clients must never automatically retry Start or infer Stop success from a lost response. Reauthenticate and read the same request/job. Consumer reconciliation binds to the stable authenticated profile/credential generation, rather than an ephemeral login session; station/AP sessions with that shared authority can reconcile. A credential change retires that scope. Engineering certificate principals, authenticated field credential epochs, and local USB physical authority remain separate scopes; neither can read or Stop another scope's tone. Authentication material and authority overrides are never supplied in tone documents. Accepted work keeps its finite native deadline if its caller is revoked.

### Conducted bench drive groups

An HP 437B Automation client can retain the original boot-active drive and saved state, verify both native schedules disabled and idle/unowned output, group points by existing drive, and restore the original drive with the same save/restart/readback sequence after the campaign. Saving drive uses the existing authenticated settings transaction with direct GP2, valid exclusive pins, healthy storage, idle/unowned inactive output, and the existing filter/amplifier requirements. Callsign, locator, a WSPR dial, and station commissioning are not required. Existing settings and network/profile authority are preserved; a healthy device without saved settings uses its validated factory hardware defaults. Local USB settings require no Wi-Fi credentials. An absent station remains absent and WSPR remains disabled. No special bench configuration or invented identity is used.

After each drive save, explicitly restart, rediscover the new boot, read current capability/configuration and boot drive, and Review/Start one carrier at a time. Verify that job's pad evidence before accepting meter readings. Budget settling/readout within the observed running interval, allowing transport age and an explicit Stop margin. Confirm native inactivity before another point or settings save; abort a group on unresolved shutdown or unverified drive. Restore the original drive through save/restart/readback without enabling schedules. Restoring a previously unsaved boot default persists that drive; it does not erase settings. Lost save/restart replies follow their existing authoritative reconciliation rules. HP sensor factors, attenuation, reference planes, and measurement acceptance criteria are outside this firmware contract.

Hardware-free fixtures cover 13 representative legal carriers at all four drives, including 5,366,200 Hz. Those synthetic carriers do not replace the HP campaign list and establish no physical RF, pad-current, timing, or power qualification.

## Authority and migration

Retain protected management/retirement channels, credentials, durable receipts, and recovery journals. Stored active WTP backend selection, enabled inbound listener, or unresolved legacy recurrence/cleanup duties refuse affected execution. Inactive dormant WTP connection values remain private storage data and must not be erased by ordinary autosave. Complete retirement with WTP-capable software before replacing it; see the managing Pi’s migration and recovery guide.

### Four-drive Si5351 testing

The ordinary `qrp-labs-rev6-25mhz-clk0` execution profile admits 2, 4, 6, and 8 mA on the existing QRP Labs Rev. 6 / 25 MHz external-XA TCXO / CLK0 setup. Drive activation still requires save, restart, rediscovery, and boot readback; Test Tone never programs a per-job drive. Start freshly verifies the selected clock-control register before RF and freezes that evidence with the accepted job. Both schedules must be disabled for each tone. Settings, register readback, numerical realization, and conducted RF observations are separate evidence. The historical all-mode matrix remains specific to its original 8 mA image and captures. Companion consumers must use the current descriptor and schema; the profile drive field is now an exact array, and old scalar-profile validators require updating.
